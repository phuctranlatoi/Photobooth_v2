# Camera baseline migration inventory (Phase A)

## Scope and evidence

This is a source/configuration audit only. V1 was accessed only with read/glob/grep; no execution, build, device access, settings change, SDK reconfiguration, or write occurred. No `.env`, customer image, or production writable Hot Folder was read. Consequently all statements below are source-level evidence, not proof of native initialization or physical-camera behavior. No physical hardware test was performed.

V2 inspection found a simulator camera/IPC foundation and an explicitly gated reflective legacy port, not a production Canon integration. The port comments state it must not be wired until approved.

## V1 alternative sources and safety-relevant behavior

- `services/StillCaptureService.kt` defines the common stream/capture surface (read this with implementations before porting).
- `services/WebcamStillCaptureService.kt:25-...` uses Sarxos webcam capture, device preference and still capture; `build.gradle.kts:17` declares `com.github.sarxos:webcam-capture:0.3.12`. Source discovery sorts DroidCam preference (also reflected in V2 `LegacyCameraPort.kt:81-90`).
- `services/HotFolderCaptureService.kt:13-...` uses a configured folder and scans for new files around capture. This path is configured via `DesktopBoothConfig.kt:18,70`; do not reuse or write to V1's configured path. Review entire implementation for readiness/stability semantics before copying; no source-level claim of robust delayed-write handling is made here.
- `services/EosUtilityCaptureService.kt:17-...` and `services/CliCaptureService.kt` are additional externally triggered sources. Operator source selection and timeout settings are represented in `DesktopBoothController.kt`, `DesktopBoothConfig.kt`, and `ui/screens/SettingsTabContent.kt`.
- V1 output processing must remain the authoritative full-resolution path. V1 Native live view currently applies `applyEffectForLiveView` before emitting; Beauty is not evidenced in the snippet, and V2 bridge previews should stay low-res/no-Beauty.
- Weaknesses to harden during port: mutable `sessionOpen`/camera operations are not uniformly serialized; reconnect can recreate while commands are active; `close()`/service disposal is not shown in this class; repeated `beginLiveView` after capture may race stream job; synchronous `.get()` may block controller caller; no explicit bounded shutdown timeout appears here.

## V2 current state and gaps

- `backend/src/main/kotlin/com/lesouvenir/v2/camera/legacy/LegacyCameraPort.kt:12-90` provides opt-in `HardwareAuthorization`, reflective Canon open/LV/download/close and webcam discovery. Construction itself does not initialize Canon; `open()` checks authorization. It has no Canon capture/shutter/download-to-output method, no status/reconnect, serialized command executor, or managed live-view lifecycle.
- `backend/src/main/kotlin/com/lesouvenir/v2/camera/simulator/SimulatorCamera.kt` plus `SimulatorSessionEngine.kt` implement synthetic fixture behavior; session engine explicitly identifies simulator-only, synthetic behavior. Existing IPC preview is simulator-focused. This is not Canon support.
- `backend/src/main/kotlin/com/lesouvenir/v2/ipc/OperatorSettingsStore.kt` defaults `nativeCamera` false; no verified production camera mode/config selecting Canon, Webcam or Hot Folder was found in backend runtime.
- V2 backend `backend/build.gradle.kts:5-13` currently declares only Gson, Kotlin coroutines and test dependencies; it does not declare Canon/EDSDK or JNA. `LegacyCameraPort.kt` uses reflection, so its class does not itself provide those runtime classes. This statement is scoped to the inspected backend Gradle dependency block; project-wide artifacts/config/docs may separately mention SDK/JNA or plans, and such mentions do not establish a resolved runtime dependency or packaged DLL. No Canon DLL payload was identified in the V2 backend inventory inspected here.
- V2 does have fixture tests (`backend/src/test/kotlin/com/lesouvenir/v2/camera/simulator/SimulatorCameraTest.kt`, `.../LegacyCameraPortTest.kt`) and bounded latest JPEG helper (`LegacyCameraPort.kt:36-50`), but no native init/discovery evidence and no physical-camera evidence.
- Shared architect IPC contract should be extended through its owner, not independently. Required future contract elements: versioned camera status/source, bounded preview bytes or latest-frame notification, capture request/result/failure; no full-res repeated IPC. Current simulator contract must not be misrepresented as hardware.

## Smallest safe migration tasks (after audit checkpoint)

1. Establish agreed versioned IPC contract and Kotlin device/controller interfaces with architecture owner; keep simulator as separate adapter.
2. In V2 only, copy/adapt the minimal permitted EDSDK4J wrapper/native dependency set after license/provenance and 64-bit/JDK compatibility review. Keep DLL loading lazy and behind explicit hardware authorization/config; fail clearly when missing.
3. Implement one serialized Canon command lane and lifecycle (initialize/discover/open, LV start/stop/latest bounded compressed preview, AF/shutter/capture/download, disconnect/reconnect, cancellation/close). Never hold the camera unless user-approved; avoid capture from UI animation callbacks.
4. Port V1 full-resolution image processing invocation and backup/naming semantics, tracing `DesktopImageProcessor.saveBoothCapture` before coding. Do not change layout-configured count/countdown or controller state machine.
5. Add isolated V2 temp-dir Hot Folder with readiness (stable size/readability), timeout and bounded retry; port Webcam alternative and operator source selection from V1 settings. Never point tests at V1 paths.
6. Progressive validation only: (A) simulator + isolated Hot Folder tests; (B) native DLL init/discovery smoke test only with explicit user approval and no device conflict; (C) controlled physical Canon test only after separate user approval and confirmation V1 is not using it. Report each level separately.
