# Business confirmation, cancellation, print, and sale baseline gates

**Date:** 2026-10-31. Source-only audit; no V1 execution, production credentials/data/calls, shell, hardware, print, or writes outside this new V2 document. This describes source behavior, not end-to-end parity or production safety approval.

## V1 observed behavior and identifiers

- Timeout is an implicit, **unconfirmed** print path: V1 `controller/DesktopBoothController.kt:291-310` fills missing selections, chooses a fallback frame if needed, then calls `startPrinting(userConfirmed=false)`.
- Explicit `startPrinting` defaults `userConfirmed=true` (`:717`); it obtains `sessionId` from `currentSessionId`, creating/storing a UUID only if absent (`:717-721`). `currentSessionId` is subsequently used for album request, upload, sale and session record (`:732-750,795-800,833-844,903+`).
- Selected layout/frame/photo paths are read for composition (`:742-756`). Print is launched asynchronously; enabled system print computes strip sheets as `max(1, requestedCopies / 2)` using integer division, otherwise copies unchanged, selects strip/full printer-name setting, calls printer service (`:758-790`). V1 service “success” is a returned Java print call, not queue or physical confirmation (see printer baseline); the controller's local `accepted` flag means only `Result` success.
- Sale snapshot uses frozen pricing if available, otherwise derives from selected layout label and `_printCopies`; includes same `sessionId`, layout, size, quantity/pricing and payment method (`:830-841`). V1 records locally only when `userConfirmed && printJob.await() && currentSessionId == sessionId` (`:842-850`). Thus inactivity auto-print can print but does **not** record a sale. A failed render/print or stale current session also suppresses local sale. Remote revenue sync is launched only after local record succeeds (`:844-849`).
- Cancellation is accepted only in `SELECTING_PHOTOS` or `EDITING` (`:926-928`), cancels Beauty/capture/inactivity/video work, clears frozen pricing and resets session, then asynchronously removes that session's V2-like local session directory when safely beneath sessions root (`:929-947`). It is not accepted in print pending/printing/delivery by this method. `finishSession` cancels delivery work and resets (`:920-924`). Back from `PRINT_PENDING` returns to `EDITING` (`:950-962`); this source section does not establish cancellation of an already-started print job.

## Current V2 boundaries

- `backend/src/main/kotlin/com/lesouvenir/v2/integrations/RevenueRecognition.kt:8-25` defines a journal and explicitly provides only `InMemoryRecognitionJournal`; source calls it not durable or production exactly-once. `:29-46` requires a nonblank sale `externalSessionId` equal to backend-observed active, confirmation, and print session IDs, explicit user confirmation, non-dry-run, and `PrintResult.Submitted`. Any mismatch/dry-run/timeout-style `Uncertain`/denial is ineligible. `:47-54` returns `ALREADY_RECORDED` for recorded ID, otherwise reconciliation required on a duplicate reservation; sink false/exception becomes reconciliation-required and is never automatically retried.
- `backend/src/main/kotlin/com/lesouvenir/v2/printing/legacy/LegacyPrinter.kt:14-27,35-45` requires backend authorization (default deny), validates explicit printer/copies and returns `Submitted` when driver call returns, `Uncertain` after submission boundary exceptions. Its own comment explicitly says `Submitted` does not confirm queueing or physical output.
- Simulator `backend/src/main/kotlin/com/lesouvenir/v2/ipc/SimulatorSessionEngine.kt:181-200` validates frontend-supplied UUIDs, session/generation and process-local seen IDs/command dedup; `:218` `print.confirmDryRun` only completes synthetic workflow and returns image data URLs. `:219-221` permits cancellation only in SELECTING_PHOTOS/EDITING and finish in DELIVERY; `:228` resets in-memory `userConfirmed=false`. It does not call printer or revenue. IDs/dedup are process-local (also baseline inventory), not durable across restart.
- `integrations/SharedApiClients.kt:8-26` has a `SaleTransaction` with external session ID and revenue methods; client code is not session/printer wired. No durable V2 integrated sale journal, print submission-to-sale orchestration, or real queue/physical confirmation was established by these sources.

## Parity distinctions and bounded safety adaptations

**Exact V1 behavior to preserve/characterize:** inactivity auto-print is unconfirmed and must not create a sale; manually confirmed sale uses the same active session ID and frozen layout/quantity/price snapshot as the print request; only the explicit condition in V1 above records local sale; cancellation eligibility and reset ownership must not be broadened accidentally. V1 considers print service `Result.success` sufficient for its local accounting condition, even though that means only the driver API call returned—not queue/physical proof.

**Safety adaptations (document as intentional non-parity):** deny-by-default print authorization; require an explicit, backend-owned confirmation/authorization record rather than trusting frontend flags; exact ID equality across active session, confirmation, print request and sale; treat post-boundary `Uncertain` as possible submission and prohibit automatic resubmission; require operator reconciliation. These tighten V1's weakly evidenced acceptance boundary and are not exact behavioral parity. They must not be presented as V1 behavior or silently alter pricing/cancel UX.

**Important limitation:** requiring `PrintResult.Submitted` remains a driver-return gate, not proof of queue acceptance, print completion, or paper output. A stricter durable business policy may choose queue confirmation, but that would be a separate design decision and requires robust queue identity/status semantics. A lost reply after successful submission must not cause retry until reconciled.

## Durable reconciliation gaps

Current V2 recognition state is process-local. Restart loses reservation/recorded/reconciliation state; concurrent processes are not coordinated by the in-memory synchronized map; sink timeout/exception may occur after remote commit; there is no durable outbox, remote idempotency contract, reconciliation query, or verified atomic relationship between accepted print and sale. A separate process-local simulator command dedup does not solve these gaps. V1 SQLite local sales is a different design (`V1 src/main/kotlin/com/phuctran/photobooth/desktop/data/SalesRepository.kt:10-42,49-66`), with unique session ID, but V1 remote sync semantics are outside this limited comparison and do not establish V2 durability or exactly-once remote writes.

## Future acceptance evidence required (offline first; no implementation here)

1. **Decision + source trace:** architect/business signoff explicitly labels parity rules vs safety deviations; trace immutable session ID and frozen pricing snapshot from confirmation through print request and resulting sale.
2. **Eligibility table tests:** no sale for dry run, inactivity/unconfirmed print, rejected/denied printer, uncertain submission, wrong/missing/stale active/confirmation/print/sale ID, canceled session, failed render, or failed/pre-boundary print. Exactly one eligible explicit confirmed same-session submission may attempt recognition.
3. **Duplicate/retry tests:** duplicate confirm/command before and after process restart; same idempotency key/request returns existing outcome without another print; key reuse with changed payload rejected; after `Uncertain` or remote timeout/exception, do not auto-print or auto-record again; surface reconciliation-required operator state.
4. **Durability/concurrency tests before production claim:** journal survives process restart and crash boundaries, atomically reserves one session across processes, records immutable sale payload/hash and print job key/state, and supports explicit reconciliation of remote committed/not-committed/unknown outcomes without duplicate accounting. Inject crashes before submit, after submit-before-response, after response-before-journal-finish, and during remote commit. Tests use local synthetic sinks only.
5. **Cancellation ownership:** test every documented state boundary; ensure selection/edit cancellation invalidates pending recognition and cleans only V2-owned artifacts, while cancellation/back after printer submission cannot assert that paper/job was canceled. Test stale asynchronous completion cannot record against a newly active session.
6. **Evidence labels:** offline tests establish contract behavior only. Real queue semantics require separately authorized, controlled hardware validation; physical output/consumption must never be inferred from `Submitted`. No production calls or real prints are part of acceptance for this audit.
