# LE SOUVENIR V2 — UI audit and implementation handoff

**Scope:** Read-only audit of `frontend/src` (customer, operator, settings). This is a specification, **not a working UI or evidence of physical hardware validation**. Preserve backend-authoritative state, payment, cancellation and print gates. No V1 files were modified.

## 1. Findings: what currently renders, and what must change

The customer application is `KioskSimulator.tsx` → `AppShell` → `screens/*`; operator is `AdminScreen`/`Operator.tsx`, with settings in `V1Settings.tsx`. `main.tsx` imports `styles.css`, `customer.css`, `stages.css`, `finishing.css`, `preview.css`, and `kiosk-v1.css`; `screens/payment.css`, `operator/operator-v1.css`, and `v1-settings.css` additionally style their respective views. The first three stylesheets retain old simulator selectors and global `button`, `header`, `h1` rules. `kiosk-v1.css` repeatedly redefines `:root`, `.v1-shell`, buttons, cards and image frames; final declarations and `!important` rules take precedence over the intended visual direction. Do **not** add another global override at the bottom. Consolidate the winning rules into a scoped customer theme and a separate operator theme, retire redundant overrides after screenshot comparison.

Specific conflicts: `kiosk-v1.css:431–540` introduces cyan/violet/neon oil-slick accents and 20–28px blur; `:root` and `.v1-shell` are overridden several times (`:114`, `:361`, `:394`, `:536`). Carousel ends at center **1.04** and sides **.95** (`:491–501`), not requested 1.08/.94. `.v1-primary` falls back to 56px (`:398`, `:565`), contrary to 64–72px customer primary requirement. `.v1-frame-grid` thumbnails can still sit on glossy white cards (`:523–525`), whereas artwork should float. `operator-v1.css:2–19` duplicates theme definitions and uses >16px blur; nav labels force `white-space:nowrap`, risking overflow at 1280×800 and 150% scaling. `v1-settings.css:5–6` uses 48/52px controls and a 58×34 switch: enlarge the **interactive wrapper** to 56px minimum; keep the switch visual track compact. `payment.css:92–139` correctly isolates an **opaque, stationary QR**, but uses 20px blur; retain opaque QR and its quiet zone, reduce blur on outer surround only. Existing customer image `object-fit:contain` and physical paper `drop-shadow` are good starting points. Do not blur, saturate, transform, or animate live pixels, captured images, frame overlays, payment QR, or print-ready composition.

Additional audit flags for frontend-coder/architect: `StartScreen.tsx:18` has a five-tap brand admin trigger; keep hidden, do not expose visible admin buttons. `PaymentScreen.tsx:80` displays a staff-tip containing a literal PIN; **remove PIN from all public UI text** and ask architect to verify where credentials and authorization are enforced (visual redesign alone cannot secure the bypass). `CaptureScreen.tsx:50` renders a centered countdown layer; the existing full-viewport overlay rules at `kiosk-v1.css:110–121` risk covering faces. `CaptureScreen.tsx:37–47` fits live image from its actual intrinsic dimensions and calculates a crop from configured `photoAspectRatio`; preserve that coordinate system, including mirror semantics. `PrintingScreen.tsx` currently highlights its first pipeline step regardless of actual backend progress; do not imply stages are completed without authoritative events. `FrameScreen.tsx:35–50` confirms on tapping the already selected frame; do not accidentally skip `frame.confirm` or `print.confirmReal`/`print.confirmDryRun`. `SelectPhotosScreen.tsx` has a 500ms hold-to-preview plus regular tap selection; retain explicit zoom affordance, release on cancel, and do not let a hold also toggle selection. Existing `KioskSimulator.tsx:51–75` queues mutations; present pending and reconciliation rather than adding a UI replay on uncertain command outcome.

## 2. Final visual system — Option A, **Atelier Canvas** (selected)

**Option A (chosen):** matte ivory photograph-first stage; editorial headline at Welcome with two unboxed overlapping **illustrative** print layouts; no frosted sheet behind imagery. In Capture, matte charcoal surrounds an aspect-fitted camera feed, a high-contrast small progress rail in the top safe band, shutter in bottom safe band, and a large countdown in the **side gutter where available**. If no gutter is available, countdown uses a bounded top/bottom safe band, never a full-frame veil over faces. At 1280×800 this retains legibility without moving/covering the crop center.

**Option B (not chosen):** gallery-magazine Welcome with a full-bleed photographic hero and translucent text plate; Capture with a centered 200px countdown disc. Dramatic, but Welcome text is less predictable with event artwork and the central disc occludes faces during posing. Only revisit with controlled imagery and face-safe camera framing proven on hardware.

Warm glass is permitted on **controls/chrome only**. Never use iridescent/rainbow gradients, neon glows or stacks of glass cards. Suggested CSS variables, scoped to `.atelier-customer` and separately aliased within `.operator-workspace`:

## 3. Geometry, imagery and responsive behavior

Use a 16:10 viewport grid with **safe outer margin 32px at 1280×800; 64px at 1920×1200** (`clamp(24px,3.33vw,64px)`); header 72–96px, bottom action dock 80–100px, content `min-height:0`, 16–32px section gap. At 1280×800 reserve at least ~500px content height after header/dock; adapt using container/available height, not only `vw`. Content scrolls **inside** choice list/payment details/settings, with fixed accessible exit action; no clipped confirmation footer or inaccessible controls. At 1920×1200, increase artwork/preview rather than leaving huge empty cards. At <1050 effective CSS px (including Windows DPI causing reduced CSS viewport), make photo/preview splits ~55/45; <900 effective px, stack only if both preview and a reachable primary action still fit, otherwise use local scroller. At ≤800 CSS px height, reduce outer padding to 16–24px and vertical gaps to 12–16px, **not** button hit size. 100/125/150% scaling must be measured from actual `window.innerWidth/innerHeight`; no assumption that a 1920-pixel monitor still exposes 1920 CSS px.

Real print artwork/frames: `object-fit:contain`, `aspect-ratio` from backend `printAspectRatio`; captured photo aspect from backend `photoAspectRatio`; image intrinsic dimensions determine live feed, not a hardcoded 3:2 box unless loading fallback. Place paper shadows **on image/artwork**, never on a large white wrapping card. Avoid clipping transformed carousel art: preserve 16px+ clear around enlarged center; first/last items must genuinely center with scroll padding. Center card `scale(1.08)`, adjacent cards `.94`, farther cards `.88` with legible labels and opacity ≥.9; arrows ≥64×64; tap card selects/centers, separate CTA advances by existing command. Scroll-snap center, nearest center indicator updates from actual scroll (not only arrow click); arrows and touch both usable. Maintain opaque white QR with renderer quiet zone, never blur/filter/scale QR bitmap.

Component props carry backend IDs/counts/statuses; do not manufacture counts, QR URLs, print completion or authenticated staff permissions in CSS/UI.

## 5. Motion, touch, safety and test checklist

- Target customer controls ≥56×56 CSS px, primary 68–72px; spacing ≥12px between adjacent destructive and safe actions. No hover-only affordance. Restrict `:hover` effects to `(hover:hover)`; use 120–180ms press feedback, carousel settle 220–300ms, no animation on video pixels or QR. Cap blur at 12–16px; avoid continuously animated backdrop filters and perpetual glow; `prefers-reduced-motion:reduce` disables pulses, transitions, smooth scrolling and decorative flash but **not** countdown text.
- Single-finger vertical list pan; horizontal carousel swipe optional with arrows; cancel hold on pointer cancel/move beyond ~12px, release outside; taps on disabled images must not trigger navigation. Use a short pending lock rather than arbitrary debounce that drops valid later actions. Haptics only behind available API and never await haptic completion before invoking capture.
- Check runtime timeout state and restored session snapshot after idle/restart. Never introduce a visual back button on capture or any state where `session.back` is rejected. Staff controls remain concealed and PIN never printed in public help. Modal escape/back closes safe overlays only; explicit destructive confirmation remains mandatory.
- Screenshot/DOM acceptance matrix: 1920×1200 and 1280×800 at Windows 100%, 125%, 150% **effective CSS viewport**; each stage with long Vietnamese/English labels, long event/frame names, empty catalogs, pending/error/disabled, portrait and landscape artwork, reduced motion and forced colors. Confirm no horizontal page scroll, cutoff primary CTA, overlapping panel, dark carousel patches, blurry print/QR, selected-card clipping, or face-obscuring countdown. Measure button rectangles ≥56/68px and composited text contrast ≥4.5:1; keyboard focus 3:1. Test photo count and countdown with *different* configured layout values (no hardcoded sample numbers). Preview QA is mock evidence only; physical camera orientation, live safe bands and DNP print status require hardware validation.

### Architect questions before code changes

1. What event/status granularity is authoritative during `PRINTING`, payment confirmation and camera reconnect? Display indeterminate state if only the session enum is available.
2. Is staff PIN authorization verified server-side for `payment.mockComplete`, and what is the approved production staff recovery text? Remove any literal PIN from screen immediately.
3. Which layout/camera modes expose mirror metadata, preview intrinsic dimensions and safe face/crop margins? Do not assume universal 3:2 or reserve a gutter that does not exist.
4. Which failure states permit `session.back`, `session.cancel`, or payment retry, and which timeout events reset/restore sessions? Only render enabled actions for existing backend-approved transitions.
