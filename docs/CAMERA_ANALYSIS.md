# V1 camera capture analysis for V2 reuse

Read-only inspection of V1 source. No build or hardware test was run. References below are under `E:\HK1_2026_2027\PhotoboothDesktop`.

## Canon EDSDK path (observed)

Primary source: `src/main/kotlin/com/phuctran/photobooth/desktop/services/NativeEosCaptureService.kt`; command extension: `src/main/java/edsdk/api/commands/SafeShootCommand.java`.

- Constructs `edsdk.api.CanonCamera()` in service initialization and immediately calls `openSession()`. Failure is logged and service still starts reconnect coroutine.
- Reconnect coroutine runs on IO scope, checks every 2,000 ms. If session false it best-effort closes, constructs a new `CanonCamera` (comment says clear dead USB reference), then opens session. If connected it probes `camera.apertureValue`; exception marks disconnected and stops live view. If reconnect succeeds and prior effect ID is nonempty and no live-view job, it calls `startLiveView`.
- Live view: `startLiveView` records effect ID, returns if session not open or job active. It calls `beginLiveView()` up to 10 tries, 500 ms apart; after success attempts property `kEdsPropID_Evf_AFMode=2L` (comment describes face-tracking AF). Polls `downloadLiveView()`, applies `applyEffectForLiveView`, publishes latest `StateFlow<ImageBitmap?>`, and flushes source image. Requested loop interval is 30 ms (~30 fps). Null frame increments count, emits error image and waits 100 ms; when `nullCount > 20` marks disconnected and stops. Exceptions emit error frames but do not increment null counter. `stopLiveView` cancels job, clears it, calls `endLiveView` if sessionOpen.
- Capture requires open session; creates output directory; executes `SafeShootCommand(EdsSaveTo.kEdsSaveTo_Host, 3)` and blocks on `.get()`. If returned array nonempty it picks last downloaded file, passes it to `saveBoothCapture(source, outputDir, shotIndex, photoAspectRatio, effectId)`, then deletes downloaded temporary source. Failure returns null; tries `beginLiveView()` again when live-view job active.
- `SafeShootCommand` checks image quality to determine one or two files (secondary type present => two); sets camera SaveTo and capacity for host/both; checks prior EVF state, sends TakePicture with retries (constructor receives 3), sleeping 1s after command error. Does not end live view (comment says preserve Servo AF). On mirror lockup sends shutter non-AF then OFF. Handles directory-item-created/request-transfer events, downloads each via `CanonUtils.download`, ignores extra events, and completes after expected count; if previous EVF was enabled, resumes it. Download destination is generated by library when not supplied.
- AF behavior: this service sends EVF AF mode property; `SafeShootCommand`'s primary take-picture command does not explicitly autofocus (CLI likewise says no-AF). Lens/camera AF configuration is external.
- Disposal gap: service has no public shutdown/close method in this file. Scope/job/native camera handles are not deterministically disposed here. `stopLiveView` does not close session. Capture blocking `.get()` has no explicit timeout/cancellation.

### Native dependencies and runtime

Exact DLL names, load order, architecture checks and licensing text were not established from the service source inspected; verify dependency/JAR contents and V1 packaging metadata before copying or shipping. ## Hot Folder

`src/main/kotlin/com/phuctran/photobooth/desktop/services/HotFolderCaptureService.kt`:

- Creates configured folder. Lists direct children before waiting and snapshots names. No camera trigger; comments state operator uses Bluetooth clicker and app waits for image.
- Polls direct children 150 times: each iteration lists files, selects first newly named `.jpg` (case-insensitive), requires nonzero size, waits 500 ms, then accepts. Poll delay is 100 ms: nominal 15 s timeout plus readiness delay. This is a fixed-size/debounce check, not a robust unchanged-size/lock test; a slowly written file can still be incomplete.
- Calls shared `saveBoothCapture` with source, configured output, shot index/aspect/effect, then deletes incoming file best-effort. File naming is delegated to `DesktopImageProcessor`; no hot-folder naming scheme is defined here. The original incoming file is consumed/deleted after processing.
- Uses JPEG bytes/source path; no EXIF-specific preservation logic is in this service. Need inspect `DesktopImageProcessor.saveBoothCapture` before asserting metadata retention.

`EosUtilityCaptureService.kt` duplicates recursive hot-folder polling and trigger behavior (below); it is not wired per controller selection found.

## CLI camera

`services/CliCaptureService.kt` builds command from `config.cliCaptureCommand.replace("%s", absoluteOutputPath)`. Default from `DesktopBoothConfig.kt`: `CameraControlCmd.exe /capturenoaf /filename "%s"`. It invokes `Runtime.exec(command)`, waits without timeout, logs exit code, but does not parse stdout/stderr or map exit codes to errors. It then polls output for up to roughly 5 seconds (50 iterations; 100 ms between; after nonzero file waits another 200 ms), processes it and deletes temp file. Missing file => null. Configurable executable/args are a single command string, so quoting/path-with-spaces handling merits adaptation; child output streams are not drained. Live preview is a separate screen-window capture loop.

## Webcam

`services/WebcamStillCaptureService.kt` uses sarxos `Webcam.getWebcams()`, names sorted to prefer DroidCam. Actual selection caches first DroidCam-named device, otherwise `Webcam.getDefault()`; there is no operator-selected exact device in this class. Opens at maximum available view size, fallback 1280x720; camera still is `webcam.image`. Capture is a synchronized direct frame read (not a hardware shutter command), center-crops to fixed 16:9, then shared processor. Preview similarly reads `webcam.image` about every 33 ms and applies live-view effect. Stop cancels job and clears preview but does not close cached webcam in this implementation.

## Live-view transport and concurrency

In V1 these services expose `StateFlow<ImageBitmap?>` in-process (Compose UI), not a network/IPC transport. Native loop requests ~30 fps; webcam ~30 fps; CLI polls captured desktop windows every 16 ms (~60fps logic); EOS Utility ~30fps. StateFlow is a conflated latest-value holder, so no explicit frame queue/backlog; frames are converted to Compose bitmaps and native source image flushed. Preview effects are applied in the camera service. There is no compression, IPC frame-size policy or capture/UI serialization contract shown. V2 bridge should retain latest-frame semantics, transmit bounded downscaled/compressed preview frames only, avoid preview Beauty, and serialize capture commands outside UI animation.

## Other capture path and configuration selection

`EosUtilityCaptureService.kt` checks `tasklist` for `EOS Utility 3.exe`; preview first captures window title `Live View`, falls back to sarxos default (OBS custom sizes preferred 1920x1080, then 1280x720, 640x480; otherwise max supported). Capture snapshots recursive `.jpg` paths, sends Space to `EOS Utility` or `Live View` window via `WindowCaptureHelper`, then polls new recursive JPGs. Triggered timeout 15s, untriggered 1s; waits 500ms after nonempty file, processes and deletes it. This source exists but controller factory does not select it in the inspected configuration branches.

Selection source `services/DesktopBoothController.kt` around lines 64-67 is priority order:
1. `useNativeSdk` => Native EDSDK
2. `useCliCamera` => CLI
3. `useHotFolder` => Hot Folder
4. else => webcam (inferred from factory branch; inspect exact surrounding lines when implementing).

`config/DesktopBoothConfig.kt`: `useHotFolder` default true, `useNativeSdk` default true, `useCliCamera` default false. Environment keys `USE_HOT_FOLDER`, `USE_NATIVE_SDK`, `USE_CLI_CAMERA`; command field `cliCaptureCommand`, env `CLI_CAPTURE_COMMAND`. Both native and hot-folder defaults true, so priority means native wins unless disabled. Settings UI exposes Hot Folder toggle, but that alone does not necessarily govern native/CLI flags. Do not read or copy V1 `.env`.

## V2 reuse/adaptation guidance

- Copy/adapt Kotlin behavior only after architecture/IPC contract is established. Preserve processor call semantics and `SafeShootCommand` behavior only if licensing permits. The Java class is custom source (not merely opaque JAR API) and addresses double-image events; do not blindly replace with library ShootCommand.
- Adapt `NativeEosCaptureService` to backend-owned `CameraDevice`/`CameraController`/`LiveViewStream` abstractions, a single serialized command executor, bounded timeouts, explicit state transitions, cancellation-safe close, native handle/session disposal, device identity selection, and deterministic reconnect. Guard reconnect/live-view/capture against races; existing shared mutable `camera` and `sessionOpen` are not synchronized.
- Adapt CLI using `ProcessBuilder` argument vectors, bounded timeout, drained stdout/stderr, explicit exit-code diagnostics and atomic/size-stability readiness; never use UI blocking thread.
- Adapt Hot Folder into watcher/poller with isolated V2 folder, snapshot/unique identity, stable size over repeated intervals, extension policy and safe retry; preserve original source backup before any destructive cleanup. Current services delete source after processing.
- Webcam remains an explicit fallback, not a substitute for Canon SDK functionality. Expose operator source selection in profile/config and report actual device.
- Preserve configured shot count/countdown in backend orchestration; these capture service methods process one shot and must not invent sequence values.
