# LE SOUVENIR — Seoul × Saigon Editorial Atelier

**Status:** presentation handoff, not implementation or a claim of visual, physical-touch, payment, printer or camera testing. Scope is the V2 sources and tests named below; no legacy workspace inspection. This specification supersedes older *visual* recommendations where they disagree, but not mounted actions or tests. Frontend coder owns implementation; architect must resolve the open contracts in §9. No new business states, payment gates or shortcuts.

## 1. Creative direction and alternatives

**A — Gallery → darkroom, chosen.** Welcome is an ivory asymmetric two-column spread: tactile invitation left, staggered paper portrait and strip right, a quiet fixed champagne halo behind them. Capture is a charcoal photographic stage, full-bleed surround with contained feed and a separate dark perimeter countdown rail. At 1280×800 the numeral is legible without covering faces. A small luminous ring is decorative, not a progress clock. The shutter stays a centered concentric tactile control within its control area.

**B — Contact sheet → centered viewfinder.** Welcome centers one large print/contact sheet above a wide action. Capture fills the screen with preview and a centered translucent numeral. More cinematic, but text competes with images and a central countdown can obscure people. Do not choose it. Both proposals preserve identical actions and timing. Existing centered countdown is tested for role/class/ticking, not a requirement to cover faces; confirm any other geometry tests before changing coordinates.

The identity is real paper, espresso typography, terracotta as signature not decoration everywhere, and thin champagne rules. Customer browsing/review may use restrained alabaster glass on **one layer** of floating controls, never on QR or photographs. Avoid moving ambient blobs, rainbow gradients, infinite breathing glows, glossy dashboard cards, photographic filters and large blurred overlays. Halo is static, low-contrast and decorative. Only authorized local V2 samples or safe backend artwork; illustrations explicitly identified as such.

## 3. Viewport, touch and motion

Design in actual CSS pixels, never a fixed bitmap or CSS zoom. At 1920×1200 / 1280×800 use no document scrollbar and keep header, work area and action rail inside viewport. Starting geometry: gutters 64/32, header 104/80, footer 104/88, body remaining after gaps 24/16. Welcome columns 46/54; content screens use approximately 55/45, adjustable for print aspect. Use `min-width:0; min-height:0`, `object-fit:contain`, grid/flex and internal scroll for potentially unbounded lists. At physical 1920×1200 scales 100/125/150%, approximate CSS viewports 1920×1200 / 1536×960 / 1280×800; physical 1280×800 gives 1280×800 / 1024×640 / ~853×533. Measure actual WebView viewport; these are estimates. At <1100 width or <760 height reduce gutters to 16–24 and compress decoration, not targets. At 720×500 and narrow/short viewports allow clearly visible **internal** scrolling for content/modal while CTA remains reachable, never horizontal document overflow. A static screenshot is not proof of fit.

Transitions: 120–180ms press compression ≤3%, ≤250ms carousel shift, no oscillation. Avoid animating images or large blurs during capture. Reduced motion removes travel, flash animation, spinner rotation and scaling; still show status and the single countdown value. Haptics only if supported, opt-in/nonblocking and never evidence of a successful operation. Hold/pointercancel must not produce a second click; carousel arrows remain accessible without swipe. Never attach global Back, Home, retake or cancel.

Shared layouts: `AppHeader` uses 56px back slot, title and optional right track; align back to first title line even if subtitle wraps. `ActionBar` reserves ≥88px and never covers scroll content. Dialogs have an opaque high-contrast surface, ≥56px buttons, default focus on non-destructive choice, focus containment/return where compatible with hold zoom, and Escape for keyboard where appropriate. Do not alter actual modal eligibility or commands. `.v1-error` is a prominent alert with the existing reconciliation action; it cannot conceal essential CTA or cause replay. PIN inputs are never logged.

## 5. CSS ownership and cleanup plan

Current `styles.css` imports Tailwind → tokens → core → customer → operator → immersive → `payment.css`. `atelier-customer.css` repeats Phase C/A/B/8/7 and older geometry, while immersive repeats the same selectors and has contradictory max-width 900 rules (two-column rule immediately followed by one-column). `payment.css` comes last with `!important`, competing with customer/immersive payment rules; core also stacks below 900. Operator has repeated Phase 9 rules. These are concrete conflicts, not separate themes.

1. Inventory computed styles and visual baselines at six viewports before edits. Keep `styles.css` as **one import graph**; do not also import older `customer.css`, `kiosk-v1.css`, `finishing.css`, `atelier.css`, `v1-settings.css` or operator-local CSS unless an actual importer requires it; inspect import graph before removing anything.
2. `theme-tokens.css`: all shared values and font aliases. `atelier-core.css`: reset, shell, shared buttons/header/actionbar/dialog/preview/timer and accessibility only. `atelier-customer.css`: one section per Welcome, layout, quantity, preparation, capture, selection, frame, confirm, printing, delivery. `screens/payment.css`: sole owner of payment + PIN (no payment rules in customer/immersive except shell's neutral shared component definitions). `atelier-operator.css`: sole operator and settings styling. `atelier-immersive.css`: delete from graph after relocating only needed reduced-motion/forced-color behavior to owners, or retain empty with comment; do not keep a second visual override layer.
3. For each selector/property/scope, define one base rule in its owner and one explicitly scoped modifier/media override only when values differ by state/breakpoint. Merge Phase C/A/B/8/7 and Phase 6 into relevant screen sections, delete dead `.v1-kicker` styling if no other use, consolidate preparation selectors around actual `:has(.v1-prepare-screen)`, move camera rules to Capture. Do not blindly delete tested selectors or shared component styling. Avoid specificity escalation, `!important` and body-wide `:has()` where a shell modifier suffices; preserve any indispensable host behavior through explicit scope.
4. Resolve responsive conflicts with a single ordered breakpoint table: ≥1100 and ≥760 standard, compact otherwise; only truly narrow/short content stacks or internally scrolls. Never apply both competing layouts at the same condition. Payment QR node has one clamp-based size owner, not both fixed 320px and clamp. Remove fixed-height text containers that clip Vietnamese; preserve stable QR geometry.
5. `liquidGlassFx.ts` delegates pointer feedback only to customer non-camera enabled controls and disposes listeners/ripples; reduce to bounded optional press feedback or remove its initializer and CSS together after checking `main.tsx` and tests. No body ambient animated orbs, no camera/operator ripple; preserve pointer/hold semantics and cleanup. No changes to session or camera code.
6. Verify computed CSS and screenshot diff per screen/state before deleting old blocks. Re-run all existing tests without altering their expectations; add viewport, contrast, real touch and image geometry tests. One screen's fixes must not reintroduce cross-file overrides.
