## Native Canon: actual call chain

* `services/NativeEosCaptureService.kt:7-8,18-48`: `edsdk.api.CanonCamera` and `EdsSaveTo`; constructor instantiates camera and immediately opens session; reconnect coroutine starts even after failure. `cameraNames` returns a static label, not discovery (`:110-112`).
* Binding source at `edsdk/api/CanonCamera.java:71-82` calls `initLibrary()` then JNA `Native.loadLibrary` with Windows stdcall; `edsdk/api/BaseCanonCamera.java:119-128` calls external `DLL_Setup.initLibrary("EdSdk")`. Exact DLL resolution/search and bundled Maven artifact equivalence to the loose `edsdk/` sources have **not** been proven. `CanonCamera.java:97-176` starts a dispatcher thread, initializes EDSDK, pumps Windows messages and a single command queue, terminates SDK on dispatcher exit. Class initialization itself therefore has side effects and may fail before service error handling.
* `CanonCamera.java:194-253,261-287`: queued open gets camera list, count, selects index zero, registers object callback, opens session, releases list; error releases camera ref. Close command closes and releases camera. `:180-192` static close interrupts/joins dispatcher. Native service has no explicit shutdown/dispose method (`NativeEosCaptureService.kt:18-236`); a shutdown hook exists in binding (`CanonCamera.java:107-115`) but is not a substitute for controlled session closure. Audit native reference ownership and error paths before adaptation.
* `NativeEosCaptureService.kt:50-81`: every two seconds reconnect closes old session best effort, recreates wrapper and opens first device; aperture property probe detects exceptions. Live view restarts only if nonempty effect and job is null. `:114-173,189-195`: begin retries up to 10 at 500 ms, sets EVF AF mode 2, downloads and effect-processes frames with 30 ms delay; >20 nulls triggers disconnect, with 100 ms null delay. Stop cancels job and ends EVF only when `sessionOpen`. Exceptions emit drawn error frames. Watch for concurrent reconnect/preview/capture, job termination versus null, stale frames and cancellation races; do not assume existing wrapper queue solves all Kotlin-side races.
* `NativeEosCaptureService.kt:84-108,197-234`: ISO, aperture, shutter speed, white balance and picture-style setters exist; suppress errors. Capture executes `SafeShootCommand(Host, 3)` and blocks on `.get()` without an explicit timeout, chooses last returned file, processes it then deletes temporary file; failure attempts EVF resume. Avoid changing device settings in normal production; EVF/SaveTo and shutter have side effects and require controlled testing.
* `src/main/java/edsdk/api/commands/SafeShootCommand.java:65-133`: determines one/two image outputs from image quality, sets SaveTo and host capacity, sends TakePicture up to three attempts with 1-second error delay; mirror-lock branch uses non-AF shutter press/release. `:135-171`: object created or transfer-request callbacks download through `CanonUtils.download`, count events, resume EVF and finish. Distinct event types may refer to the same item; event-counting, null downloads, missing callback and multi-format order need characterization. Do not blindly retry an uncertain shutter result: it can duplicate a shot. Separate timeout from proof of cancellation.

## Other input paths

* **Webcam:** `services/WebcamStillCaptureService.kt:39-52,73-130` enumerates sarxos cameras, prefers DroidCam then default, caches choice, opens largest reported size, center-crops preview and still to 16:9, processes preview at approximately 30 fps, synchronizes still capture. Stop cancels preview but does not close cached device. Dropped frame errors are ignored; unplug/cache recovery is not explicit.
* **Hot Folder:** `services/HotFolderCaptureService.kt:24-29,36-76` has no live view and no automatic trigger; operator uses Bluetooth clicker. Snapshot names, poll top-level new `.jpg` every 100 ms up to 150 iterations; first nonzero file gets a fixed 500 ms wait, processed and deleted. This is not a stability/readability check; ordering, concurrent writes, `.jpeg`, duplicate events and delayed files are not robustly handled. Use isolated V2 directory; never delete V1 input. Readiness must verify stable size/mtime and decode, bounded retry and session ownership, with defined late-file policy.
* **CLI:** `services/CliCaptureService.kt:24-49,58-98` returns static name; captures third-party window for preview; substitutes destination in configured command, executes it and waits without process timeout, then polls nonempty JPEG for up to 5 s with fixed 200 ms wait; processes and deletes temp. Exit code is logged rather than enforced. External command security and lifecycle require review.
* **EOS Utility alternative:** `services/EosUtilityCaptureService.kt:29-39,43-113,115-167` checks `tasklist` for EOS Utility, captures a Live View window or default webcam, sends space to EOS window, recursively polls new JPEG (15 s triggered, 1 s otherwise), fixed 500 ms wait then deletes. It is defined but not selected by controller's cited factory; do not claim an active mode. Window automation/other process ownership and licensing require approval.

## Original, processing, orientation

`controller/DesktopBoothController.kt:1180-1203` sends session root `data/sessions/<session>` to capture; `imaging/DesktopImageProcessor.kt:19-57` decodes source, applies effect/LUT then horizontally mirrors and JPEG-encodes `Photo_<index>.jpg`. Although parameter `photoAspectRatio` is passed, it is not used by this save method. Native temp and Hot Folder input are deleted after processing (`NativeEosCaptureService.kt:211-219`, `HotFolderCaptureService.kt:66-74`); therefore this path does **not** preserve a byte-identical camera original. The controller calls resulting processed file an original for Beauty (`controller/DesktopBoothController.kt:557-564`); the `originals` folder at `:511` is specifically the dummy fallback, not proof of native raw backup. Preserve V1 processed output plus a separately retained untouched transfer in V2; this backup is a deliberate safety improvement, not claimed V1 parity. LUT failure falls back to unfiltered (`DesktopImageProcessor.kt:60-78`). Determine EXIF orientation/metadata and preview display mirroring separately; no EXIF handling is shown in the cited processing path. Preview uses effects, not Beauty; preserve appropriate effect behavior without Beauty.

## Proposed adapter boundary — subject to architect contract

Kotlin sidecar is plausible because integration is JVM/JNA and Windows-message-loop based, but remains **unproven**, particularly class-load path, packaging, native threading, independent device ownership, crash shutdown and IPC. Propose `CameraDevice` for identity/capabilities and explicit ownership, `CameraController` for serialized lifecycle/capture and `LiveViewStream` with latest-frame bounded delivery. Architect defines versioned commands/events and frontend types; no schema is established here. Commands should include profile selection, discover/open/close, preview start/stop and capture with session/shot/request identity; typed status, failure, preview and capture completion events must support stale-generation rejection, deadline/cancellation semantics and restart reconciliation. Explicit device busy/unavailable, uncertain capture outcome, timeout, disconnect and recovery states; no blind hardware retries. Native command actor must coordinate property access, reconnect, capture and close, with bounded waits and correct dispatcher ownership. Stop/release once, account for in-flight callbacks, and isolate potentially hung native operations in restartable sidecar. Avoid opening a camera used by V1.

Preview should scale/compress to negotiated bounds and drop old frames instead of queueing full-resolution images; status travels separately. Original transfers stay on V2-owned storage, associated with session/shot, not repeatedly sent over IPC. Keep processing off UI animation and preserve processed JPEG/LUT/mirror behavior with independent backup. Mode switching, file cleanup, retry semantics and profile persistence require architect agreement.
